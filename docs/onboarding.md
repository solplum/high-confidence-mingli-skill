# Onboarding — 首次建档流程

> 触发：个人分析需要建档，而 `~/.claude/fortune-telling/chart.md` 不存在，或已有档案缺少本次所需输入。
> 目标：保存可复核的输入、实际可得命盘与未决项，再按 `workflows/fortune-auditable-reading.md` 完成个人分析。
> 确定性字段由 `scripts/` 引擎产出；建档不等于已经完成深入分析，程序结构摘要也不是完整详批。

## 第 0 步：说明用途与数据位置

向用户简要说明：八字、紫微和七政是不同的传统解释体系，先分别核查，再对照一致、冲突与缺口；跨盘相同不构成独立验证或预测准确率。可用单盘或两盘继续，不必等三盘齐全。

引擎脚本在本地执行，个人档案与本次证据存放于 skill 仓库之外的 `~/.claude/fortune-telling/`。使用云端 agent 时，被提供给模型的出生信息、命盘及反馈依所选服务的数据政策处理，不能承诺全部数据永不离开本地。安装依赖或查询外部资料也可能联网；不主动把个人资料传给排盘网站或提交到公开仓库。

## 第 1 步：采集并固定原始输入

一次询问当前缺少的信息，已有可靠记录不重复索取：

| 字段 | 用途与处理 |
|------|------------|
| 称呼 | 可选，昵称即可，不影响排盘 |
| 性别参数 | 引擎用于传统排运顺逆；不能据此假定性格、伴侣性别或婚姻结果 |
| 出生日期 | 标明公历或农历，农历须区分闰月；保留用户原始说法及转换来源 |
| 出生时间及误差 | 记录钟表时间、来源及明确的 ±N 分钟或区间；不知道就保留未知，不填默认时刻 |
| 出生地 | 地点与经纬度来源；城市坐标不冒充出生医院的精确位置 |
| 出生当时时区 | 确认 IANA 区域或实际 UTC 偏移，核对可能的夏令时；不把当前时区当出生时区 |
| 时间口径 | 默认民用时间；平太阳时或真太阳时须明确选择。确认输入是否已校正，避免重复换算 |
| 分析范围及年份 | 具体问题、时间范围；涉及年度字段时显式固定分析年，防止三盘目标年错位 |

完整总控 `build_chart.py` **只接收公历 `--solar`，且 `--hour` 必填**。八字独立脚本支持 `--lunar`，不代表总控可直接接收农历。只知农历时，先核对转换所得公历日期及闰月，再传给总控；相关历日风险见 `docs/historical-calendar-audit.md`。转换无法确认时保留缺口。

### 时间不确定或未知

- 已知中心时刻和误差：中心只作一个候选。明确误差在 ±120 分钟内且完整 UTC 区间在1901–2099年时，可用 `--enumerate-scenarios --uncertainty-minutes N` 比较四柱及紫微离散输入；这不覆盖起运、完整紫微、七政或天文模型误差。
- 只知一个时辰或宽时间段：保存原区间，检查实际相关的时辰、换日和节气边界，不用区间中点替代唯一命盘。区间无法映射到支持的枚举输入时，保留人工待核分支，不自行缩窄误差。
- 完全不知时辰：可用八字独立脚本的未知时辰路径生成六字资料，不运行需要 `--hour` 的总控：

  ```bash
  python3 scripts/pai_pan_bazi.py --solar 1990-05-15 --sex 男
  ```

  该独立 CLI 按其北京时间口径处理，不能假装具备总控的 IANA/太阳钟面接口。保存实际输出及命令，时柱为未知；年/月边界与起运使用内部参考时刻，不能把输出起运岁数当已知。其他地区、节气或换日边界未解决时，可能变化的柱也保留为候选；不要把参考时刻当真实出生时间。紫微和七政缺少足够时间时保留缺盘，禁止从性格或已知事件倒推唯一时辰。

## 第 2 步：按明确的时间契约执行引擎

输入足够时，在本次用户证据目录保存总控 JSON，不只保留 Markdown 摘要。例中日期、时间和坐标均为演示输入，`Asia/Shanghai`、民用钟面与分析年应按本次已确认信息选择：

```bash
cd <本 skill 目录>
python3 scripts/build_chart.py --solar 1990-05-15 --hour 14:00 --sex 男 \
    --lat 31.23 --lon 121.47 --place 上海 --timezone Asia/Shanghai \
    --time-basis civil --analysis-year 2026 --format json
```

记录实际命令、引擎版本/源码摘要、依赖锁摘要、原始输出、warnings 和缺盘原因。需另生成人类可读 `chart.md` 时使用相同输入和口径运行文本格式，不手改引擎字段。

总控的实际职责：

1. 八字引擎产出四柱、十神、藏干、大运、农历和警告；`bazi_core_reading` 提供有限结构、格局候选和窄强弱证据，不自动完成喜用或完整详批。
2. 七政引擎产出其已声明坐标和学派口径下的天体、命度、宫、昼夜等数据。近似宿宫边界和条件规则的限制照录，不据数字位数宣称精确。乾元宫主参照必须明确选择，不能自动替换度主法。
3. 紫微引擎产出十二宫、固定生年四化、大限及实现规则；首次在 `scripts/pai_pan_ziwei` 执行 `npm ci`。四宫主题模块不是完整星曜组合或运限分析。

紫微依赖缺失或执行失败时保存具体原因，按可用盘继续。需要外部命盘时核对其版本、历法、钟面和学派，把导入内容当待核证据。无 Python 或无法运行引擎时，可保留用户已有盘并注明不能校验的字段，或暂停相关判断；口算不替代引擎，不能据此交付正常深入分析。

## 第 3 步：检查钟面与时间边界

先读 `docs/time-contract.md`。默认 `--time-basis civil --utc-offset 8` 不自动采用真太阳时。`--timezone` 可代替固定偏移；重复民用时间须明确 `--fold 0/1`，不存在的时间不能自动平移。

只有显式选择 `--time-basis mean-solar` 或 `--time-basis apparent-solar`，修正后的日期和钟面才进入八字日时与紫微离散输入；节气、起运及七政天体位置保留原始瞬间。七政安命仍保留 +08 民用时辰口径，不能随太阳模式一起改学派。秒数显示或数值求根容忍不代表独立验证过的秒级天文精度。

有明确误差时运行支持的候选比较，区分模型内稳定字段、变化字段和未覆盖字段。真太阳时候选只有数值见证、未证明穷尽，`observed_constant_fields` 不能当稳定。七政可在支持范围内另加 `--qizheng-sensitivity --uncertainty-minutes N`，保留采样限制。无法检查的边界明确写出，不默认影响很小。

## 第 4 步：核对输入与盘面

向用户展示原始输入、所选钟面、四柱及可用盘的关键字段、时间分支与缺口，确认是否录入错误。格局和喜用不是此步可直接确认的排盘数字。

用户有 App 结果时可对照，但不承诺必然一致：先比较时区、夏令时、历法、晚子时、四化表、坐标和七政盘制。记录实际差异及可查原因；不为凑一致手改输出，也不以 App 或本仓单方结果自动裁决。差异未解决时保留候选解释或暂停依赖它的判断。

## 第 5 步：有依据地建立解读记录

先遵守 `knowledge/README.md` 的来源门，再按 `workflows/fortune-auditable-reading.md` 与 `templates/reading-workpad.template.md` 建立本次工作记录。所有个人分析默认深入核查，用户只要求短答时压缩呈现，不降低核查深度。

- 以实际引擎字段建立事实；结构摘要和旧 `<!-- agent: -->` 占位不自动授权填满格局、调候、强弱或喜用。
- 每个重要判断记录适用规则、具体来源、前提是否满足、反向信号、竞争解释和适用边界。未决就保留未决，不用“一句推理”变成定论。
- 按本次问题逐领域记录覆盖状态。单盘先分别形成第一版判断，再单独复审字段、来源、条件和遗漏；可用独立 agent 时提供快照和记录复审，无并行工具时顺序执行并保留复审结果。
- 通过实际执行的 ledger 校验只说明相应结构检查结果，不证明自然语言、古籍真伪或预测能力。未运行的检查如实标明。
- 记忆中分开保存用户自述、已确认事实与传统解释假设；不把盘面推导的性格种子当实际用户画像，不把用户已告知事情包装成独立发现。

正文按主题解释“为什么、在什么条件下、有哪些反向信号、边界在哪里”，再给与现实条件相符的建议。依据与缺口足够说明后交付，不按耗时或引用数量验收，不把无法完成的模块写成已经分析。

## 第 6 步：可选反馈与版本保留

用户没有样例或选择跳过时继续完成建档与本次分析，不重复索取，不以反馈状态升降可靠度或计算准确率。若愿意参与，先冻结判断、时间窗和未命中标准，再完整记录命中、未命中及信息不足。已知事件只作回顾；修订解释保留版本，不改引擎盘面或原始资料。只在用户同意时保存反馈。

## 第 7 步：保存并交付实际完成状态

1. 在用户数据目录保存 `chart.md`、需要的 `memory.md`，以及本次快照、来源索引、工作记录、ledger 与复审/校验结果；六字或导入路径只保存实际取得的产物，不伪造总控 JSON。
2. 已有文件先读取，更新时保留原始输入和历史版本；不因新增证据目录移动、覆盖或重建旧档案。
3. 告知哪些数据和分析已经完成、哪些仍有条件或缺口。建档完成可以进入各模式，但每次个人问题仍执行同一深入核查标准。

## 维护操作（非首次）

| 用户说 | 操作 |
|--------|------|
| “重新建档 / 重置命盘” | 保留原档版本与用户反馈，再按新的已确认输入建档 |
| “修改出生信息” | 确认改动，重跑相关引擎及候选比较，撤回或重审受影响判断，不沿用旧解释 |
| “补充紫微/七政数据” | 检查原缺盘原因与新数据口径，运行可用引擎或核对导入数据，再补做相应分析与复审 |
